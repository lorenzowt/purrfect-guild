# AI Development Log — Purrfect Guild

## Introduction — AI-Assisted Development Methodology

### Why I Chose Codex

For the development of Purrfect Guild, I chose OpenAI Codex as my primary AI coding assistant.

One of the main reasons was the practical consideration of token usage and available usage limits. I also already had experience working with Codex, making it a familiar tool that fit naturally into my development workflow.

Beyond these considerations, Codex offered several technical advantages for this project:

- **Project context:** It could inspect the existing codebase and understand relationships between components, configuration files, and documentation.
- **Multi-file implementation:** It could implement features across React components, TypeScript types, API services, styles, and tests.
- **Development tooling:** It could execute commands, run automated tests, check TypeScript errors, and verify production builds.
- **Incremental development:** It supported working on individual features while following the project's Gitflow workflow.
- **Iterative refinement:** I could review generated implementations, identify problems, and request targeted corrections without rebuilding entire features.

These capabilities made Codex suitable for developing a React and TypeScript frontend connected to an existing Laravel REST API.

### Development Methodology

Before generating application code, I worked with ChatGPT to define the project's requirements, architecture, visual identity, and user flows.

This planning process produced several documents that served as references throughout development:

- `PROJECT_BRIEF.md` — Project objectives, concept, and scope.
- `DESIGN_SYSTEM.md` — Visual identity and interface guidelines.
- `USER_FLOWS.md` — Player interactions and application navigation.
- `ARCHITECTURE.md` — Technologies, structure, and technical decisions.
- `AGENTS.md` — Instructions and development rules for Codex.
- `openapi.yaml` — Contract describing the existing Laravel API.

Rather than asking AI to generate the entire application in one request, I divided development into smaller phases and feature branches.

Each phase followed a similar process:

1. Define the feature and its requirements.
2. Provide Codex with the relevant project documentation.
3. Generate the implementation and automated tests.
4. Review the functionality and visual results.
5. Identify problems or differences from the intended design.
6. Request corrections and verify the results.
7. Commit the completed feature using Gitflow and Conventional Commits.

I used ChatGPT primarily for planning, structuring implementation prompts, understanding technical concepts, and documenting the development process. Codex was responsible for generating and modifying the application code.

### My Role in the Development Process

Although much of the frontend code was generated by AI, the process required continuous human involvement.

I made decisions about the application's functionality, architecture, visual identity, and user experience.

I also evaluated generated results, identified usability problems, requested corrections, and reconsidered earlier decisions when the implementation revealed better alternatives.

Some examples included correcting modal behavior, improving mission navigation, changing the administrator experience, synchronizing frontend behavior with backend changes, and refining responsive layouts.

Automated tests were used throughout development, but I also reviewed the application manually because passing tests did not always mean the user experience matched my expectations.

### Learning Objectives

An additional motivation for documenting this process was to understand the advantages and limitations of AI-assisted development.

I wanted to explore how effectively AI could translate structured requirements into a functional application, while learning to identify and evaluate the technical decisions made during implementation.

The development process demonstrated that AI can accelerate implementation, but clear specifications, human judgment, testing, and iterative feedback remain essential.

**The objective was not simply to generate a working frontend, but to understand how to guide, evaluate, and improve AI-generated software while maintaining control over the final product.**

## Interaction 04 — Frontend Architecture

**Phase:** Technical Planning  
**AI Model:** OpenAI GPT-6  
**Purpose:** Define the frontend architecture, select development tools, and establish coding and testing practices.

### 1. Initial Prompt

I asked the AI to help plan the technical architecture of Purrfect Guild, focusing on code organization, API integration, authentication, state management, styling, and testing.

My goal was to create a maintainable React application that connects to my existing Laravel API without unnecessary backend changes.

### 2. AI Recommendations

The AI presented different architectural approaches, explaining their advantages and disadvantages. It recommended:

- Separate repositories for the frontend and backend.
    
- React Router for navigation and protected routes.
    
- Axios, TanStack Query, and OpenAPI-generated TypeScript types for API integration.
    
- React Context and built-in hooks for state management.
    
- Feature-based code organization with reusable components.
    
- Tailwind CSS and Motion for styling and animations.
    
- Vitest, React Testing Library, MSW, and Playwright for testing.
    

### 3. My Decisions

After comparing the alternatives, I accepted the recommended architecture.

For authentication, I chose **in-memory Passport token storage**, understanding that users will need to log in again after refreshing the page. This avoids storing authentication tokens in browser storage.

I also decided to use **pragmatic TDD**, prioritizing tests for important gameplay interactions while using visual inspection for decorative elements.

### 4. Outcome and Reflection

With AI assistance, I created `ARCHITECTURE.md`, establishing the project's technical structure, development conventions, security considerations, and testing strategy.

This process helped me better understand the responsibilities of different frontend tools, particularly the distinction between API communication, server-state management, and local React state.

I also learned that architectural decisions involve tradeoffs between simplicity, maintainability, security, and user experience.

## Interaction 11 — API Synchronization and Mission Data Refinement

**Phase:** Development — Phase 7 Finalization  
**AI Model:** OpenAI Codex  
**Purpose:** Improve mission ordering, expand API response data, and synchronize the frontend with backend changes.

### 1. Initial Problem and Decisions

After implementing Phase 7, I identified two limitations in the Laravel API:

- Missions were not guaranteed to appear newest-first across paginated results because sorting was performed in React after pagination.
- Mission responses did not include the heroes' classes, which would be useful for assigning consistent character portraits throughout the application.

I decided to correct these issues directly in the Laravel backend rather than introducing additional frontend workarounds.

### 2. Backend Changes

I modified the Laravel API to:

- Sort missions by creation date in descending order before pagination.
- Include `hero_class` alongside the existing hero information in mission responses.

These changes improved data consistency and provided the frontend with the information needed for future portrait integration.

### 3. AI-Assisted Frontend Updates

I instructed Codex to synchronize the frontend with the updated API.

The requested changes included:

- Updating `openapi.yaml` to reflect the expanded mission response.
- Regenerating the TypeScript types.
- Removing unnecessary client-side mission sorting.
- Reviewing mission-related components to use the updated response structure.

### 4. My Intervention and Corrections

During the implementation, I encountered an issue with how Codex interpreted the additional API field.

Because `hero_class` was now available in mission responses, Codex attempted to display it in more places throughout the interface.

However, **adding information to an API response does not necessarily mean that information should be visible to the player**.

I clarified that the hero class was primarily needed for internal frontend logic, particularly future portrait selection, and should only be displayed where it was already appropriate according to the design.

This required explicitly separating the data available to the application from the information presented in the user interface.

### 5. Outcome and Reflection

The frontend was updated to reflect the improved API contract, and mission ordering could now be handled correctly by Laravel rather than separately on each frontend page.

This interaction highlighted an important limitation of AI-assisted development: AI may interpret newly available data as an opportunity to expand the interface, even when that was not requested.

I learned that backend data structures and frontend presentation have different responsibilities. An API should provide the information needed by the application, while the interface should selectively display what is relevant to the user.

**My main takeaway was that providing more data should not automatically result in showing more data.** Clear instructions and critical review are necessary to prevent AI-generated changes from introducing unnecessary interface elements or deviating from the intended design.

This also reinforced the value of making architectural corrections in the appropriate layer rather than relying on frontend workarounds.

## Conclusion — Reflections on AI-Assisted Development

Developing Purrfect Guild with AI was a valuable experience that helped me understand both the advantages and limitations of AI-assisted software development.

One of the most successful decisions I made was **dividing the project into smaller, clearly defined development phases**. Rather than asking AI to generate the entire application at once, I established the requirements, architecture, design system, and user flows beforehand, then implemented each feature separately.

This approach gave me a greater sense of control over the development process. I could review each feature, identify problems, and make corrections before moving forward. Whenever I noticed a difference between my original intentions and what the AI had generated, I could also update the project documentation and instructions to prevent the same mistake from appearing in future implementations.

I found this particularly effective for maintaining consistency across the application. As development progressed, the documentation became increasingly useful as a shared reference between my decisions and the AI-generated code.

However, **the biggest limitation I encountered was the difficulty of making precise, small-scale changes to the frontend**.

While Codex was very effective at implementing entire features, refining specific visual details was often surprisingly time-consuming. Adjusting card proportions, spacing, or responsive layouts sometimes required multiple prompts, and correcting one problem could introduce another.

I realized that achieving this level of control often required either a very precise technical explanation of the underlying CSS and component structure or the ability to modify the code myself. Without that technical understanding, I sometimes spent hours describing changes that might have taken only a few minutes to implement manually.

The Mission Journal was the clearest example of this limitation. After several unsuccessful visual adjustments, the situation only improved when I asked Codex to investigate the actual CSS rules, component structure, and rendered dimensions instead of continuing to make changes based on visual descriptions.

This experience changed how I view AI-assisted development. I believe AI is an excellent tool for accelerating the initial implementation of software, especially when requirements are well documented and tasks are clearly scoped. However, it does not eliminate the importance of understanding the code being generated.

In fact, **the more precise the control I wanted over the final result, the more valuable my own technical knowledge became**.

Overall, I consider the project a successful example of AI-assisted development. I was able to create a complete React and TypeScript frontend connected to my Laravel API, while remaining involved in the architectural, functional, and visual decisions.

At the same time, the experience motivated me to study React and TypeScript more deeply, with the goal of being able to understand, maintain, and refine the generated application independently.

**My final conclusion is that AI can significantly accelerate software development, but the best results come from combining its implementation capabilities with the developer's technical knowledge, judgment, and creative direction. AI is most useful when it increases a developer's capabilities, rather than replacing their understanding of the software they are building.**
